# nano-mimiclaw from Scratch

> 从零手撕一个跑在 $5 芯片上的 AI agent

## 全书结构

### 第一章：六个文件，各管各的

**目标**：读完知道每个模块是干嘛的，脑子里有张地图。

**内容**：
1. 先看全貌：总共 6 个 C 文件，一千行上下，对标 MimiClaw 的几千行
2. 每个模块一段话讲清楚"做什么"和"不做什么"：
   - `bus.c`：消息总线，通道和 agent 之间的搬运工
   - `llm.c`：跟 Anthropic API 说话的翻译官，进去是 messages，出来是 blocks 加 stop_reason
   - `tools.c`：工具注册表加三个纯函数工具
   - `memory.c`：MEMORY.md 长期记忆和 JSONL 会话
   - `agent.c`：整个项目的灵魂，一个 while 循环
   - `main.c`：胶水层，把上面五个粘起来
3. 跟 MimiClaw 的对应关系，砍了什么、为什么砍
4. 一张架构图（文字版）

**篇幅**：~1500 字

### 第二章：从一个 while 循环开始

**目标**：从数据流出发，一步步拼出完整代码。不是"我给你看代码"，是"我们需要什么，就造什么"。

**行文线索**：

1. **起点：agent 到底是什么？**
   - 一句话定义：能调工具的 LLM，自己决定下一步做什么
   - 核心就是一个循环：问 LLM → 模型说 tool_use → 调完把结果喂回去 → 再问
   - 十行以内的伪代码，把骨架亮出来

2. **第一个问题：消息从哪来？**
   - 引出 `bus.c`，为什么通道和 agent 之间要隔一条总线
   - `mimi_msg_t` 的所有权转移是怎么回事
   - 对比 MimiClaw：两条 FreeRTOS 队列 vs nano 的一条环形数组

3. **第二个问题：模型怎么知道自己是干嘛的？**
   - 引出 system prompt：人格 + MEMORY.md + 工作方式
   - Context 是什么：纯 JSON 的消息数组，可落盘可恢复

4. **第三个问题：怎么跟 LLM 说话？**
   - 引出 `llm.c` 的 `llm_chat()`
   - Anthropic Messages API 的请求体长什么样
   - 响应怎么拆成 content block 数组，stop_reason 为什么关键

5. **把循环补完整：agent loop**
   - 回到伪代码，把真实代码填进去
   - 跑一遍"现在几点？"的具体例子，看 Context 怎么一条一条长起来

6. **工具从哪来？**
   - 引出 `tools.c`，注册表和纯函数的设计
   - 为什么是这三个工具：get_time、web_search、memory_write
   - 工具输出必须是字符串，因为要塞回 Context 发给模型

7. **记忆和会话**
   - MEMORY.md 进 system prompt，session JSONL 逐聊天存历史
   - 为什么 JSONL，为什么只保留最近 20 条

8. **边界情况**
   - 工具不存在、请求失败、tool_use 死循环
   - 每种情况 agent 怎么收尾

9. **最后把它们粘起来：main**
   - REPL 走一遍总线，ui 回调是 agent 和界面的协议
   - 换个消费者就是另一种"前端"，agent 一行不用动

**篇幅**：~5000 字

### 第三章：跑起来看看（可选）

**目标**：实际跑一遍，看数据怎么流的。

**内容**：
1. 环境准备：make，设 API key
2. 不花钱的玩法：本地 mock LLM
3. 看 MEMORY.md 和 session.jsonl 里存了什么
4. 生成 trace，去教学网站打断点

**篇幅**：~1000 字

## 写作约束

- 中文为主，技术术语保留英文（Context、tool_use、stop_reason 等）
- 不用破折号（——），用逗号或句号断句
- 禁止翻案腔："不是A而是B"、"不在于A在于B"、"与其说A不如说B"、"看似A实则B"。判断从正面下，直接说结论
- 避免 AI 味的总结句、过渡句和元叙述（"让我们来看看"、"总结一下"、"接下来"、"用大白话说就是"、"简单来说"之类，直接说事情本身）
- 语气像在跟朋友讲，偶尔可以粗一点（"这破玩意儿"、"别管那些花里胡哨的"）
- 代码块只放关键片段，不贴完整文件（完整代码在 src/）
- 每引入一个新概念前，先用一句话说清楚"为什么需要它"
- 不要反复说同一件事。一个信息在最合适的地方讲一次就够了
- 不提前透露后面章节才展开的设计细节
- 段落式写法为主，少用列表
- 适当用图辅助理解，先用 `[图：xxx]` 占位描述，后续替换为正式图
- 专业术语首次出现时用 `>` 引用块加注释，用一两句大白话解释清楚
